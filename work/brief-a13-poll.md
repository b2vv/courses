# Brief A13 / крок 4c — UI перестає опитувати, поки задача в черзі

Частина A13 (Phase 8). Шостий дефект ядра, знайдений e2e кроку 4b (Courses 2, 2026-09-24).
Бриф — сесія Courses 1; рецензент, гейти й повторний e2e — Courses 2.

## Дефект (перевірено проти коду)

`frontend/src/app/composition/admin-draft-queries.ts:32-35`: `refetchInterval` опитує лише коли
поточний стан уже `running` або `pending`. Але бекенд до `Claim` не має рядка чернетки й повертає
`state: null` (`backend/internal/transcript/application/draft.go` `GetDraft`: `!lesson.Found` →
порожній статус). Стан `pending` фронтенд знає (`domain/transcript/draft.ts:1`), а бекенд його
**ніколи не віддає**. `queued` є лише в `CHECK` міграції 00008, його ніхто не пише.

Потік: «Generate» → 202 → `onSuccess` інвалідовує → один refetch бачить `null` (воркер ще не взяв
задачу) → `refetchInterval` = `false` → опитування вимкнене назавжди. Воркер доводить чернетку до
`ready`/`no_speech`, а UI лишається на `null` до ручного reload. Доведено e2e: бекенд у логах
закінчує розпізнавання, UI — ні. Блокує C03, C13 і всі speech-e2e. Дефект латентний з A10: він
ховався, поки бекенд не доходив до чернеток.

## Зроби (фронтенд, без бекенду)

1. **Клієнт знає, що задачу прийнято.** Успішний `regenerate` (202) і відповідь
   `already_running` (409) обидва означають «задача в польоті». Для цього уроку тримай опитування,
   доки сервер не віддасть **кінцевий** стан (`ready`, `no_speech`, `failed`). Відповідь `null` у
   цей час — не кінцевий стан, а «ще не взято».
2. **Показуй це авторові** як `pending` («Queued for recognition»), поки сервер віддає `null`. Це
   правда: сервер задачу прийняв. Не вигадуй інших станів.
3. **Стеля.** «В польоті» не може тривати вічно: якщо задачу втрачено, наприклад після очищення
   Redis, опитування має зупинитися. Постав обмеження в часі з назвою й коментарем (порядку
   хвилин; `TaskTimeout` бекенду має мінімум 300 с, `application/recognize.go`). Після нього —
   звичайна поведінка (`null` = немає чернетки).
4. Де тримати ознаку «в польоті» — вирішуй сам, у межах архітектури. Server state — у Query, не в
   Zustand; жодних глобальних змінних (AGENTS.md). Один урок не впливає на інший. Якщо вибір
   неочевидний — `## Discussion`.
5. **Unit-тести:** після `regenerate` при `null` від сервера опитування триває і UI показує
   `pending`; на `ready` зупиняється; 409 `already_running` теж вмикає очікування; після стелі
   зупиняється; інший урок не опитується.

## Відома межа (не фіксуй, назви в звіті)
Автопостановка (`EnqueuePending`, раз на 60 с) ставить задачу без дії автора. Якщо сторінка вже
відкрита, клієнт про це не знає, і стан з'явиться лише після reload чи refetch on focus. C03
говорить про те, що бачить автор після постановки; фікс покриває постановку, ініційовану автором.

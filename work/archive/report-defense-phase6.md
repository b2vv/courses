## Прогін пʼяти питань

### Q1 — кривий інпут
ЗАКРИТО рядками: R18 (309) не-UUID → 400 без звернення до БД; R17 (308) невідомий урок → 404;
R10 (301) `..`/подвійне кодування в медіа-шляхах → 403/404; R06–R09 (297–300) протухла/чужа/
не-та/підроблена кука → 403 без розрізнення; рядок 232 (явні бізнес-коди); 234 (zod на межі).
НЕ ЗАКРИТО:
- Тіло запису прогресу. Немає жодного рядка про `position_seconds` < 0, NaN/Inf, не-число,
  більше за тривалість. D-5 (167-168) свідомо переносить обрізання на ЧИТАННЯ, отже на записі
  валідації не описано взагалі; §5 (197-198) не називає жодного CHECK у новій таблиці.
  R20 (311) закриває лише «чужий урок → 403».
- Джерело тривалості. Порог 95% (166) і обрізання (167) потребують тривалості, якої в БД НЕМАЄ.
  Єдине наявне джерело — `video.duration` у браузері, тобто НЕДОВІРЕНИЙ інпут: ним можна
  позначити урок переглянутим із будь-якої позиції. Спека свідомо лишила діру «перемотати в
  кінець» (spec 180), але не «збрехати про тривалість». Рядка немає.
ВЕРДИКТ: дірка.

### Q2 — відмова залежності
ЗАКРИТО: Redis — D-4 рядок 158 («Redis недоступний → authorize відповідає 403») + R12 (303).
ЧАСТКОВО/ХИБНО: Go — рядки 189 (кеш 30 с) і R11 (302, «403, не 200»). Але при недоступному
апстрімі `auth_request` дає клієнту 500/502: у 403 мапляться ЛИШЕ 401/403 від сабреквесту.
У сніпеті D-2 (95-110) немає ні `error_page`, ні `proxy_intercept_errors`. Властивість «байтів
не видано» тримається, але спостережуваний критерій R11 як записаний не справдиться.
НЕ ЗАКРИТО:
- **Postgres.** D-3 умова 3 (144) — це читання БД (урок → курс → статус). Що відповідає
  `authorize`, коли Postgres лежить, не сказано НІДЕ: ні в §3, ні в §4 (таблиця сайд-ефектів
  згадує Postgres лише як навантаження, 193), ні в §8. Симетричного до 158 рядка немає.
  Так само не сказано, що буде із записом прогресу при недоступній БД (B14 (281) — це втрата
  мережі в клієнта, не відмова БД на сервері).
- **«Відповів повільно».** Жодного таймауту для auth-сабреквесту план не називає. Глобальні
  `proxy_connect_timeout 2s` / `proxy_read_timeout 15s` (`nginx.conf:32-34`) успадкуються, але
  15 с стопор на кожен сегмент — це не рішення, а випадковість, і в плані її немає.
- Що бачить ГЛЯДАЧ, коли сегменти почали віддавати 5xx/403 не через витіснення (D-4 155
  описує лише сценарій витіснення).
ВЕРДИКТ: дірка.

### Q3 — гонка й повторний виклик
ЗАКРИТО (половина «повторний виклик»): D-5 163-164 — UPSERT по PK + «останній запис перемагає»;
166 — `completed_at` не знімається ніколи (ідемпотентно); B08/B09 (275-276) — тротлінг записів;
R21 (312) — heartbeat не-власника → 409; B13 (280) — привидна сесія не блокує.
НЕ ЗАКРИТО (половина «гонка»):
- **Два одночасні `play` того самого акаунта.** Рядок 152: «`play` перезаписує ключ безумовно».
  При простому SET обидва виклики повертають успіх, обидва клієнти вважають себе власником, і
  програвший дізнається лише за ≤30 с. Хто виграє, чи атомарний запис, чи повертає він
  витіснену сесію — не сказано. P13 (262) — ПОСЛІДОВНИЙ сценарій (A, потім B), не одночасний.
- **Гонка витіснення vs продовження доказу.** Рядок 151: ключ «поновлюється heartbeat'ом» —
  без застереження, що поновлення дозволене лише коли ключ ще тримає МІЙ sessionId, і без
  вимоги атомарності (умовного EXPIRE в Redis нема без Lua/WATCH). Літера рядка 151 дозволяє
  безумовне поновлення, а це саме той баг, який знімає серверну гарантію G5.
- **Подвійний клік на `play`.** Дві сесії, два `Set-Cookie` на те саме імʼя; якщо перша
  відповідь прийде останньою, користувач витісняє САМ СЕБЕ й бачить «запущено на іншому
  пристрої». Рядка немає.
- Запис прогресу не привʼязаний до володіння: 163-164 відмовляється від злиття, спираючись на
  G3, але G3 керує володінням ПЕРЕГЛЯДОМ, а не ендпоїнтом прогресу; R20 (311) привʼязує запис
  лише до доступу до курсу. Плюс переупорядкований/повторений запит відмотує позицію назад.
ВЕРДИКТ: дірка.

### Q4 — порожні та граничні дані
ЗАКРИТО: B01 (268) курс без уроків; B02 (269) урок без відео; B03/B04 (270-271) processing/failed;
B05 (272) рівно 95% / 94.9%; B15 (282) стеля 40×120; B13 (280) порожній Redis / привидна сесія;
дублікати рядків неможливі через PK (163).
НЕ ЗАКРИТО:
- **Користувач без жодного прогресу — стан продакшена в день 1.** Жодного рядка. P02 (251)
  припускає «перший переглянутий», P04/P05 (253-254) — збережену позицію. D-6 (172-174) обіцяє
  віддати «позицію й позначку», але контракт для ВІДСУТНЬОГО рядка (0? null? поле відсутнє?)
  не описано ні в D-6, ні в §8.
- **Тривалість невідома або 0.** Наслідок факту про БД: для активу, обробленого до цієї фази,
  або коли проба не дала тривалості, правила 166 (95%) і 167 (обрізання) не визначені.
  B06 (273) припускає відому нову тривалість.
- Модуль із нулем уроків (B01 — це нуль МОДУЛІВ); позиція рівно == тривалості.
ВЕРДИКТ: дірка.

### Q5 — rollback
ЗАКРИТО: §6 рядки 211-217 — покомпонентний відкат (edge / Go / міграція / Redis / фронт);
рядок 215 явно називає єдиний незворотний ефект (втрата прогресу) і умову, за якої його роблять;
219-220 — найдешевший аварійний хід; 200 — `down` = `DROP TABLE`; 202-204 — безпечний порядок
викатки; 206 — канарка міграції й відкоту за зразком B07/B08.
ЗАСТЕРЕЖЕННЯ (не окрема дірка, а залежність): твердження 215 «єдина незворотна втрата»
тримається лише доти, доки міграція справді «лише додавання нової таблиці» (197). Якщо факт
про відсутню тривалість змусить додати колонку у `video_assets` + бекфіл, §5 і §6 треба
переписати. Дрібніше: кука `playback` у браузерах переживає відкат до 3 хв (самоспливає) —
Redis у таблиці названий (216), кука — ні.
ВЕРДИКТ: закрито.

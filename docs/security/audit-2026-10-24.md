## HIGH

### H1 — 2FA online brute-force bypass (auth) — VERIFIED (code + verifier)
`internal/identity/application/identity.go:90-94` — on the 2FA-required login path,
`Login` calls `limiter.Reset(loginRateLimitKey)` on every correct password.
`two_factor.go:124` — the only 2FA-code rate limit is keyed `"two-factor:"+PendingID`
(per-pending); `StartLogin` mints a fresh `pendingID` each login. There is NO
per-user/global cap on TOTP verifications.
- Trigger: attacker holds the password of a 2FA-enabled account.
- Exploit: loop `Login(password)` → fresh pendingID + login counter reset → 5 code
  tries → repeat. Second factor's brute-force protection effectively removed (VerifyTOTP
  window ±1 ≈ 3 valid codes / 1e6, unlimited attempts).
- Test state: `two_factor_test.go:209` asserts the literal key `"two-factor:pending"`,
  which *cements* the vulnerable per-pending design and would block the fix — it does not
  flag the hole. (Mutation: a per-user key swap is KILLED by that test — the design is
  pinned, which is the problem.)
- Fix: key the 2FA limit on `pending.UserID` (or a per-user failed-2FA counter) and move
  the login-limiter `Reset` into `CompleteTwoFactor` success; update test:209.

### H2 — bullet-list lesson documents fail to render (data/UX) — VERIFIED end-to-end
`internal/course/domain/document.go:86` `Ordered bool json:"ordered,omitempty"` drops
`ordered:false`. GET `getDraft`/`getPublished` (document_handler.go:46,133) embed
`domain.LessonDocument` and re-marshal → the field disappears for bullet lists. FE
`frontend/src/modules/document/adapters/document-schema.ts:48` requires `ordered:
z.boolean()` in a `.strict()` union. Editor emits `bulletList → pmListToBlock(node,false)`
(ui/tiptap-document.ts:114).
- Impact: any lesson document containing a **bullet** list fails zod on read → editor
  reload (getDraft) and learner render (getPublished) return `invalid_request`; the
  document won't open. Numbered lists (`ordered:true`) survive — which is why e2e missed it.
- Fix (BE, preferred): `json:"ordered"` (drop `omitempty` on a discriminator). Alt (FE):
  `z.boolean().optional()` + `?? false`. Failing-test: bullet-list → save → reload +
  publish → learner view.

### H3 — zod 4.5.4 memory-exhaustion CVE (dependency) — scanner govulncheck/npm audit

### SA01 — H1 2FA brute-force bypass — pre-code checkpoint (2026-10-24)

- **Stage:** plan. **Root/HEAD:** `fix/player-upnext-eyebrow-clip @ 1bc2f24` (tree == audit snapshot
  `0d26f07`; dirty only in deliverables + AI Factory WIP, none in `backend/internal/identity/`).
- **Scope (closed file set):**
  - `backend/internal/identity/application/two_factor.go` (`CompleteTwoFactor`, `allow`)
  - `backend/internal/identity/application/identity.go` (`Login` 2FA-required branch :90-94)
  - `backend/internal/identity/ports/two_factor.go` (`PendingTwoFactor` struct) — only under Option 1
  - `backend/internal/identity/adapters/redis/pending_two_factor.go` (serialization) — only under Option 1
  - `backend/internal/identity/application/two_factor_test.go` (:199 rewrite) + new login test
  - `backend/cmd/api/main.go` — read-only confirmed (no change: loginLimiter already shared)

- **Mechanism (confirmed by reading code, not assumed):**
  - `main.go:132-144` injects ONE `loginLimiter` instance (limit **5 / 15 min**) into BOTH
    `identity` (login key `loginRateLimitKey(email,ip)`) and `twoFactor`
    (`TwoFactorDependency.Limiter`). Same limiter, two key namespaces.
  - **Bug A** — `identity.go:91` calls `limiter.Reset(loginKey)` on the *2FA-required* branch,
    i.e. before the second factor. An attacker who knows the password logs in repeatedly; each
    call succeeds on password, mints a fresh `pendingID` via `StartLogin`, and *clears the login
    counter* — so the 5/15min login cap never trips.
  - **Bug B** — `two_factor.go:124` keys the 2FA attempt budget on `"two-factor:"+PendingID`.
    Each fresh `pendingID` (minted freely via Bug A) gets its own 5-guess budget. Combined =
    effectively unlimited TOTP guesses → 6-digit TOTP brute-forced → 2FA bypassed.

- **Fix (two parts):**
  - **Part 1 (Bug B), unambiguous:** in `CompleteTwoFactor`, `Take` the pending FIRST, then
    `allow(ctx, "two-factor:"+pending.UserID)`; on rate-limit `Put` the pending back (mirrors the
    existing failed-proof restore at :146-152). Budget becomes per-account, independent of how
    many pendingIDs exist.
  - **Part 2 (Bug A), has a design fork (OPEN — owner decision required):**
    - **Option 1 (recommended): plumb the login key into the pending.** Add
      `LoginRateLimitKey string` to `PendingTwoFactor`; `Login` passes it through `StartLogin`;
      `CompleteTwoFactor` on *success* calls `limiter.Reset(pending.LoginRateLimitKey)`. Remove
      `identity.go:90-94`. Keeps reset-on-success parity with the non-2FA login path; the attacker
      never reaches success so never resets. Cost: one port field + its Redis (de)serialization +
      `StartLogin` signature. Matches the task's stated intent ("перенести Reset у CompleteTwoFactor
      success").
    - **Option 2: no reset for 2FA logins.** Just delete `identity.go:90-94`; login counter TTLs
      out after 15 min. No schema change. Cost: a legitimate 2FA user who logs in >5 times / 15 min
      is briefly login-limited (mild UX regression; relevant to repeated e2e logins).
  - Either Part-2 option is sufficient on its own to close Bug A; Part 1 independently caps the
    per-account TOTP budget at 5/15min. With both, a brute-forcer gets ≤5 TOTP guesses / 15 min /
    account (~10^6 space → intractable).

- **Grilling / open questions:**
  1. **Part-2 fork: Option 1 vs Option 2?** (author recommends Option 1.) **OWNER DECISION.**
  2. Restore-pending-on-rate-limit in Part 1: confirmed consistent with the atomic-Take restore
     already in the code (:146-152). No new question.
  3. `allow` ordering move (before→after `Take`): a non-existent/expired pending now returns
     `ErrAuthenticationRequired` *without* consuming budget. pendingID is 32 random bytes
     (unguessable), so this is not an enumeration avenue. Resolved.

- **Proposed failing tests (TDD red, written after owner picks Part-2 shape):**
  - Rewrite `TestCompleteTwoFactorRateLimitsRepeatedInvalidProofs` (:199): assert limiter key ==
    `"two-factor:"+twoFactorUserID` (HEAD uses `"two-factor:pending"` → RED). Shape-independent;
    writable now.
  - New `TestLoginDoesNotResetRateLimitUntilSecondFactor`: fake limiter records `Reset` calls;
    assert the 2FA-required branch does NOT reset the login key (HEAD resets at :91 → RED).
  - Option 1 only: new `TestCompleteTwoFactorResetsLoginLimitOnSuccess`: assert a successful
    second factor resets `pending.LoginRateLimitKey`.
  - Impact of per-account budget across fresh pendings: assert N StartLogin→Complete cycles share
    one `"two-factor:"+userID` budget.

- **Verification plan:** `make test` (identity unit) after red→green; because this touches shared
  auth behavior and the Redis pending serialization (Option 1), the full ordered `make check`
  incl. **full e2e** before merge; HIGH/auth → independent review before merge (per task footer).

- **Admission: BLOCKED on open question #1 (Part-2 fork). Not READY until owner picks Option 1/2.**

**Decision (2026-10-24, owner):** Part 2 = **Option 1** (plumb `LoginRateLimitKey` into

**Green phase (2026-10-24, Courses 1) — implemented, gate GREEN.** Both parts shipped:
- **Part 1 (Bug B):** `CompleteTwoFactor` now `Take`s the pending FIRST, then
  `allow(ctx, "two-factor:"+pending.UserID)` (per-account, not per-pending); on a rate-limit it
  restores the pending (mirror of the failed-proof restore). `two_factor.go`.
- **Part 2 (Bug A, Option 1):** `PendingTwoFactor` carries `LoginRateLimitKey`; `Login` passes it

- Net: a brute-forcer gets ≤5 failed TOTP/recovery attempts / 15 min / account (~10^6 space →

**Regression caught by the full e2e (the reason shared-auth changes run the whole set).** First

`application/identity_test.go`, `adapters/redis/pending_two_factor_integration_test.go`.

**Residual limitation (magnitude, per AGENTS rule).** The `"two-factor:"+UserID` budget is reset
on *every* successful second factor, and the key is shared per account, so a legitimate victim's
successful login zeroes any failures an attacker has accumulated against that same account. The
effective cap is therefore "5 failed attempts *between the victim's successful logins*, or 15 min,"
not a flat 5/15 min. Magnitude: with K victim logins per window the attacker gets up to 5·(K+1)
verified guesses; against the ±1 TOTP window (~3 valid codes / 10^6, ~3·10⁻⁶ per guess), K=10 →
~55 guesses → ~1.6·10⁻⁴ success probability per 15-min window — orders of magnitude below the
unbounded H1 and intractable in practice. Mechanism forcing this: the `RateLimiter` interface only
`Allow` (atomic increment) + `Reset`; the gate must run *before* the proof is verified (otherwise a
capped attacker's guess is still checked against the TOTP and could match), so a success cannot be
distinguished from a failure except by refunding via `Reset`. Resetting on success is the price of
closing the Acc26–Acc29 legitimate-user regression. M1 (fail-open limiter) would amplify this but is
a separate finding outside SA01's scope.

### SA02 — H2 bullet-list lesson documents fail to render — pre-code checkpoint (2026-10-24)

- **Stage:** plan. **Root/HEAD:** `fix/sa02-bulletlist-document` off `main @ cf52af0` (post-SA01).
- **Confirmed by reading code (not assumed):**
  - `course/domain/document.go:86` — `Ordered bool json:"ordered,omitempty"`. For a bullet list
    (`ordered:false`), `omitempty` drops the field at marshal. `getDraft`/`getPublished`
    (`document_handler.go:67,149`) return `domain.LessonDocument` re-marshaled by `WriteJSON`, so the
    field disappears on read. Ordered lists (`ordered:true`) survive — why e2e missed it.
  - `frontend/.../document-schema.ts:48` — the list block is `z.object({type, ordered: z.boolean(),
    items}).strict()` in a discriminated union: `ordered` is **required**, so a list block without it
    fails zod → `invalid_request` on getDraft (editor reload) and getPublished (learner render).
  - The FE schema is *deliberately stricter* than OpenAPI (`LessonBlock.required: [type]` only —
    `ordered` optional in the contract) and its header states it "refuses a payload the server should
    never have produced." So the strictness is intentional defense, and the server omitting `ordered`
    for a list is the actual bug.

- **CRITICAL — the audit's literal fix is unsafe.** `Ordered` sits on a **shared** `Block` struct
  (paragraph/heading/list). Dropping `omitempty` naively would emit `"ordered":false` on *paragraph
  and heading* blocks too; the FE paragraph/heading schemas are `.strict()` with **no** `ordered`
  key, so they would reject it — a NEW break on the common case, worse than H2. Any BE fix must emit
  `ordered` **only for list blocks**.

- **Fix — design fork (OPEN, owner decision):**
  - **Option A (recommended): BE, keep the strict FE guard.** Add a custom `MarshalJSON` to
    `domain.Block` that serializes `ordered` (true or false) only when `Type == list`, and omits it
    for paragraph/heading (preserving today's shape for them). Honors the repo's defensive-FE
    philosophy (the server now always produces the self-describing list block the strict schema
    expects) and the audit's BE preference, without the shared-struct trap. Cost: one method +
    `encoding/json` import in domain (stdlib — allowed). Stored JSONB benefits too (repo marshals the
    same struct). No FE / OpenAPI / Orval change.
  - **Option B: FE, align zod to the actual contract.** `document-schema.ts:48` →
    `ordered: z.boolean().optional()`, and `?? false` at the two mapping sites
    (`document-mapping.ts:45,113`; `LessonDocumentView.tsx` reads the mapped domain, unaffected).
    Matches the OpenAPI (ordered optional) but loosens the intentional strictness; the wire stays
    "absent = bullet". No BE change.
  - Both are correct and sufficient; neither needs an OpenAPI/Orval change (openapi already has
    `ordered` optional, flat `LessonBlock`). Historical stored bullet lists read back correctly under
    either (Go unmarshal defaults false; under A re-marshal then emits it).

- **Grilling / open questions:**
  1. **Option A (BE marshaler) vs Option B (FE optional)?** Author recommends A. **OWNER DECISION.**

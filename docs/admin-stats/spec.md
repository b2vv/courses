## Проблема

Адмін платформи курсів не має жодного аналітичного екрана. На беку **немає жодного
stats / aggregate / summary / time-series ендпоінта** (звірено з кодом 2026-10-10): admin-API
розкиданий по модулях (`/admin/courses` у course, користувачі в identity, тощо) і складається
лише зі списків та редакторів. Частина списків — offset-пагінація з `pagination.total`, частина —
cursor **без total**. Orders має лише `/learn/orders/{id}` поштучно — **admin-агрегату замовлень
чи доходу немає взагалі**.

Наслідок: без нового беку чесно показуються лише ~6 чисел (users×3 статуси + courses×3 статуси).
Усе цінне — розподіл за роллю, членства (grants), замовлення/дохід, залученість, навантаження
модерації, будь-що **в часі** — недосяжне. Кільце на один status-count — косметика, не аналітика.

Платформа має реальні дані (акаунти, курси, grants, orders, скарги, медіа-стани), але адмін їх
не бачить агреговано. Потрібен backend stats-шар і екран, що його показує, **без вигаданих чисел**.

## Користувацькі сценарії

Актор: **платформний адмін** (роль `admin`; інструктор і студент на `/admin/analytics` не ходять).

1. **Знімок стану платформи.** Адмін відкриває `/admin/analytics` і за один погляд бачить
   поточні числа: скільки акаунтів (активні/заблоковані/видалені, за роллю, верифіковані, з 2FA),
   скільки курсів (чернетки/опубліковані/архів), членства за станом, замовлення за статусом і дохід,
   відкриті vs закриті скарги, медіа за станом обробки.
2. **Тренд у часі.** Адмін обирає метрику (нові реєстрації / enrollments / замовлення / дохід) і
   період та бачить, як вона змінювалась по днях або тижнях (sparkline / бар по бакетах).
3. **Чесна деградація.** Якщо для картки даних нема (ендпоінт ще не покриває метрику, або таблиця
   без `created_at` для тренду), картка показує явний плейсхолдер «потребує stats-ендпоінта», а
   **не** вигадане чи оманливе число.
4. **Solo-платформа.** На платформі з одним інструктором (конфіг-прапорець) вимір «інструктор»
   прихований: без секції «Інструктори», без per-instructor leaderboard, Overview курсо-центричний.
   Віджети спроєктовані З виміром інструктора, прапорець лише ПРИХОВУЄ (поява 2-го лектора не
   вимагає переробки).

## Acceptance criteria

**Backend — знімок.**
- A1. `GET /api/v1/admin/stats` під admin-авторизацією повертає знімок із реальних SQL-агрегатів
  (не заглушки): `users{active,blocked,deleted,byRole{student,instructor,admin},verified,twoFactor}`,
  `courses{draft,published,archived}`, `grants{active,blocked,revoked}`,
  `orders{pending,paid,failed,revenueMinorUAH}`, `reports{open,resolved}`,
  `media{processing,ready,failed}`. **revenueMinorUAH = SUM(amount_minor) WHERE status='paid'**
  (валюта UAH; реальний enum orders — `pending`/`paid`/`failed`, звірено зі схемою 00011_payment.sql,
  НЕ approved/declined/refunded — то був WayForPay-callback-словник, не наша таблиця).
- A2. Не-admin (гість / student / instructor) отримує відмову. Авторизація — **строгий
  admin-only гейт** `identityHandler.RequireAdministrator` (403 `grant_forbidden` для не-адміна),
  НЕ course-`adminActor` (той пускає інструктора).
- A3. Числа узгоджені з наявними списками: напр. `users.active+blocked` = `pagination.total`
  з `users.list` без фільтра (той самий дефолт виключення `deleted`); доводиться e2e на seed-даних.

**Backend — тренди.**
- A4. `GET /api/v1/admin/stats/timeseries?metric=<>&bucket=day|week&from=<>&to=<>` повертає
  `[{bucketStart, value}]` для метрик signups / enrollments / orders / revenue, з `date_trunc`-бакетів.
  **Часова колонка per-метрика:** signups=`users.created_at`, enrollments=`course_grants.granted_at`
  (у grants нема created_at — схема 00011:35), orders=`orders.created_at`, **revenue=`orders.paid_at`
  WHERE paid** (дохід бакетується коли гроші реально отримані, рішення власника round 2).
- A5. Порожній або майбутній діапазон, невідома метрика, перевернутий `from>to`, занадто широке
  вікно (> ліміту бакетів, визначеного в plan) — явна бізнес-помилка або порожній масив, не 500 і
  не мовчазне «0».
- A6. Усі задіяні таблиці мають придатну часову колонку (звірено: users/orders/courses/
  participant_reports/video_assets = `created_at`; course_grants = `granted_at`), тож метрика не
  випадає через брак часу. Жодних підроблених бакетів для даних, яких нема.
- A6b. **Базова довжина відео (домен «Операції», рішення власника 2026-10-10):** знімок додає
  `media.totalDurationSeconds` і `media.avgDurationSeconds` (також медіана, якщо дешево) з
  `video_assets.duration_seconds`, рахуючи `WHERE duration_seconds IS NOT NULL` і чесно підписуючи
  покриття (поле nullable до публікації). watch-through ratio, гістограма розподілу довжин,
  per-course/tag — ВІДКЛАДЕНО (`admin-analytics-tags-popularity.md` §4).

**Frontend — `/admin/analytics`.**
- A7. Новий маршрут `/admin/analytics` у NorthWind-shell (S0): hero-банд (ui-stat) + картки-секції
  §4 плану (Люди / Контент / Доступ і продажі / Залученість / Модерація / Операції).
- A8. Кожна картка живиться реальним числом зі stats-ендпоінта; картка без покриття деградує чесно
  (плейсхолдер), ніде не рендериться вигадане число.
- A9. Тренд-віджети (sparkline/бар) живляться timeseries; без даних — чесний плейсхолдер.
- A10. Прапорець single-instructor **будується в цій фазі** (env-конфіг → SSR → клієнт; наразі
  такого plumbing нема взагалі). Віджети проєктуються З виміром «інструктор»; прапорець лише
  ПРИХОВУЄ (секцію, колонки, leaderboard). За замовчуванням `true` (платформа зараз solo).
- A11. Доступність: axe 0 порушень; клавіатура; видимий фокус; світла/темна; 200% zoom (як решта
  admin-екранів).

**Гейт.**
- A12. Ordered `make check` зелений (format→lint→typecheck→test→integration→check-generated→build→
  up→seed→smoke→e2e); нові числа доведено e2e по production-шляху (не фікстура, не directory-stat).

## Out of scope

- **Дашборд / Overview як курована підмножина** — похідний від повного `/admin/analytics`, робиться
  ПІЗНІШЕ (рішення власника §8.1.4). Тут — повний розділ.
- **Retention / drop-off по відео** — потребує подієвого збору позицій відтворення, якого нема.
- **Conversion visit→buyer** — нема обліку переглядів sales-page узагалі.
- **Per-video / per-lesson аналітика** — поза знімком платформи.
- **Матеріалізація / кеш-інвалідація знімка** — знімок рахується COUNT при запиті (для платформи
  цього розміру дешево); кеш — можлива пізніша оптимізація, не вимога.
- **Нові метрики поза каталогом §2 плану** — лише перелічені домени.
- **Популярний курс, теги (курсу/відео), аналіз по тегах, аналіз по довжині відео** — свідомо
  відкладено (рішення власника 2026-10-10, «перенести на пізніше, щоб не роздувати план»). Аналіз
  і фазування — `docs/design/admin-analytics-tags-popularity.md`. Теги взагалі не існують у схемі
  (нова продуктова фіча); популярність і довжина відео мають джерела, але йдуть окремою аналітичною
  фазою. Нічого з цього не входить у admin-stats.

## Вирішені питання (GATE 1, власник 2026-10-10)

1. **Крос-модульний агрегатор — ВИРІШЕНО:** новий dedicated модуль `backend/internal/adminstats`
   із власним repo, що читає read-only `COUNT(*) … GROUP BY` по таблицях raw SQL (precedent:
   orders-repo джойнить чужі таблиці). Отримує `dependencies.Database (*pgxpool.Pool)`,
   реєструється під `RequireAdministrator`. Деталі меж — у `plan.md`, критикує GATE 2.
2. **created_at-покриття — ВИРІШЕНО:** усі задіяні таблиці мають придатну часову колонку
   (див. A4/A6). Жодна метрика не випадає.
3. **Orders-агрегат — ВИРІШЕНО (обсяг):** net-new SQL у adminstats-repo (orders має лише
   per-id lookup). Статуси й revenue — за A1.
4. **Гілка доставки — ВИРІШЕНО:** продовжити `feat/admin-reconstruction` (UI залежить від S0).
5. **single-instructor — ВИРІШЕНО:** будувати прапорець цієї фази (A10).

## Відкрите (plan-рівень, не блокує GATE 1)

- **Ліміт timeseries-вікна** (щоб уникнути `bucket=day` × 10 років): конкретний cap — у `plan.md`.
- **Визначення engagement-метрик** (активні учні / середній прогрес / завершення): точні SQL-означення
  (що є «активний», як рахувати avg progress) — явні припущення в `plan.md`, звірка з даними orders-repo.
- **Джерело single-instructor-конфігу** (env-змінна, дефолт, SSR-канал до клієнта) — у `plan.md`.

## Очікуваний результат (дописати нижче в цей файл)
1. **Критика поточного дизайну** — редактор і reader окремо, конкретні проблеми (не загальники),
   кожна з прив'язкою до файла/рядка або скриншота.
2. **Ранжований план «привести в порядок»** — від найбільшого ефекту; кожен пункт: що саме, якими
   наявними примітивами/токенами, чому так (узгоджено з React Aria + токенами, БЕЗ Tailwind/shadcn).
   Розділити **quick-win** (CSS/токени/примітиви, малий ризик) від **потребує дизайн-проходу** (нові
   патерни, можливо нова фаза). Якщо для drag-полотна/drag-реордеру потрібна залежність — назвати її й
   альтернативу на React Aria (напр. list reordering), але пам'ятати: власник окремо розглядає drag-полотно
   як МАЙБУТНЮ фазу; цей аналіз — про «навести лад» у наявному секційному редакторі, не про канвас.
3. **a11y-прогалини** — конкретні (фокус, 44px, зум 200%, світла/темна, сирий file-input).
4. Що НЕ варто чіпати / поза скоупом.

### Крок 1. Факти дизайн-системи та критика редактора

ФАКТ: прочитано редактор, rich-text, конвертер, reader, модель, специфікацію та реалізації UI-примітивів; переглянуто всі три надані JPG. Це **system**: автор складає й публікує урок, учень читає матеріал. Основний прийом майбутнього оформлення: чітка повторювана межа редагованої секції; у reader — безперервна читацька колонка. Палітру, шрифти й оболонку не переобирати. Орієнтир — опис у `spec.md:27–31`, а не виміряна відповідність зовнішньому сайту. Для anti-slop-перевірки: DESIGN_VARIANCE=3, MOTION_INTENSITY=1, VISUAL_DENSITY=5 для автора / 3 для читача; анімація не потрібна, щільність автора не означає менші цілі натискання.

ФАКТ: джерело токенів — `frontend/src/app/styles/tokens.css:1–109` (колір, шрифти, радіуси, відступи, мінімальний контроль); тема клієнта — `data-theme` і `prefers-color-scheme`; поверхні — `data-surface`. Примітиви експортуються з `frontend/src/presentation/ui/index.ts`. Стилістичний спосіб — іменовані CSS-класи, семантичні custom properties та React Aria data-атрибути.

**Два розходження брифу з кодом, не привід мовчки змінювати вимоги:**

- `frontend/src/app/styles/main.css:1` фактично імпортує `tailwindcss`. Отже, твердження «Tailwind у репо немає» не відповідає цьому файлу. Вимога цього рев’ю «БЕЗ Tailwind/shadcn» залишається чинною: усі пропозиції нижче — звичайний scoped CSS + токени; міграція глобального CSS сюди не входить.
- `frontend/src/app/styles/tokens.admin.css:10–14,29–55` документує owner-рішення від 2026-10-09 й примусову dark-only адмінку, незалежно від `data-theme`. Це суперечить light/dark у брифі та `spec.md:74–76`. Світлий editor не можна назвати перевіреним; потрібно узгодити вимогу перед реалізацією. Reader має перевірятися в обох темах. У цьому аналізі не скасовую жодної з вимог і не переробляю NorthWind.

#### 1. Критика: редактор

1. **Немає видимих меж редагування — найбільша проблема.** `LessonDocumentEditor.tsx:188–257,330–379` має класи для header/actions/section/bar/columns/add, `LessonDocumentRichText.tsx:59–131` — для toolbar і редактора, але пошук у `frontend/src/app/styles/` не знаходить жодного правила `lesson-editor`, `ProseMirror` чи `tiptap`. На `editor-text-only.jpg` редагований текст схожий на звичайний підпис; на `editor-text-image-row.jpg` три секції зливаються. Виправляти насамперед межі, відступи й площу вводу, не додавати декор.
2. **Усі рівні дій мають майже однакову вагу.** Save/Publish, порядок секції, форматування, додавання колонки й додавання секції стоять щільно один під одним (`LessonDocumentEditor.tsx:189–257,334–377`). Червоне видалення повторюється біля кожного блока, тоді як тип секції — звичайний span. Немає видимого підпису палітри: `fieldset` отримує лише `aria-label` (:239,367–370). Два ряди Text/Image наприкінці Row на JPG важко розрізнити за призначенням. Уточнення брифу: палітра колонок одна на весь Row, не на кожну колонку.
3. **Row не показує композицію, яку автор створює.** Контейнер із `data-columns` існує (:331), та без CSS колонки залишаються вертикальними div. У reader вже є дво-/триколонковий grid. Автор не бачить співвідношення зображення й пояснення; потрібно узгодити редакторський layout із reader, не обіцяючи pixel-perfect WYSIWYG.
4. **Зображення оформлене як сирий HTML.** `ImageField` (:400–424) використовує нативні input без `.ui-input`/`.ui-field`; JPG буквально показує злипле «Upload imageChoose file». Поле alt візуально губиться, preview-клас не має правила для обмеження картинки. Вже є готові `FileUpload` (`ui/controls.tsx:255–267`) і `TextField` (:47–54); новий upload-віджет не потрібен.
5. **Форматування не має видимого активного стану.** Bold/Italic/h2/h3/list виставляють `aria-pressed` (`LessonDocumentRichText.tsx:65–105`), але CSS не стилізує pressed для цих кнопок; `data-pressed` означає натискання, не активну текстову марку. Сім рівнозначних кнопок на кожен rich-text забирають увагу. Спершу wrapping, групування й активний стан; згортання в спільний toolbar — окремий патерн.
6. **Немає підтвердження результату й контексту уроку.** Заголовок загальний (:190), пропси несуть лише lessonId і queries (:22–25), успіх save/publish змінює token (:152–175), але не показує повідомлення. Автору не видно, чи зміни лише локальні, збережені або опубліковані. `busy` спільний для обох кнопок (:185–196), upload до нього не входить. Стани слід моделювати чесно, не виводити «Опубліковано» лише з наявності draft.updatedAt.
7. **Посилання може зникнути через помилку вводу.** `applyLink` (`LessonDocumentRichText.tsx:52–56`) на невалідний URL виконує `unsetLink`, закриває поле і не показує помилку. Це конкретна проблема взаємодії, не косметика: помилкову адресу слід лишити у відкритому полі з поясненням; видалення посилання має бути окремою дією.

РІШЕННЯ (Codex, рекомендація 2026-10-13): першим слайсом пропоную scoped оформлення наявної секційної структури й переюз полів UI-kit. Перевірка рішення: на тих самих трьох типах секцій без drag користувач одразу відрізняє межу секції, поле вводу, її дії та дві палітри. Це рекомендація до виконання, не нове затверджене owner-рішення.

ДАЛІ: звірити reader з layout уроку, межами наявного e2e і токенами; дописати критику reader та ранжований план.

### Крок 2. Критика reader і ранжований план

#### 1. Критика: reader

1. **Текстовий матеріал поступається службовим станам.** На `reader.jpg` найпомітніша фраза — «This lesson has no video yet», а далі заголовки Transcript/Discussion. Власне матеріал і завдання — два непримітні рядки. `routes/learn.$.tsx:266–290` послідовно ставить player → document → transcript → discussion. Для уроку без відео це виглядає як незавершена сторінка, хоча text+image — легітимний сценарій (`spec.md:22–23`). Локальне оформлення документа допоможе, але пріоритет порожнього player/транскрипта потребує окремого дизайн-рішення в оболонці уроку.
2. **Task не має власного вигляду чи видимого позначення.** `LessonDocumentView.tsx:39–49` рендерить text і task однаково, різняться лише class/data-атрибутами; правила `.lesson-document-task` немає. Це не лише смак: Q7 (`spec.md:134`) обіцяє стилізований rich-text. Завдання потребує стриманого відокремлення і підпису, але не checkbox/кнопки здачі, яких модель не підтримує.
3. **Немає локальної системи прозової типографіки.** `main.css:1352–1379` задає лише gap між секціями, зображення й grid; немає ритму p/h2/h3/ul/ol усередині rich-text, оформлення посилань чи обмеження довжини текстового рядка. Глобальні `h2` (:61–65) не розрізняють урок і панелі оболонки. Семантичні списки вже є (`LessonDocumentView.tsx:108–114`), але потребують явних маркерів/відступів під наявним CSS reset. На JPG немає списків чи h3, тож їхній конкретний зламаний вигляд **не доведено скриншотом**.
4. **Row реагує на ширину viewport, а не доступної колонки.** `main.css:1373–1378` вмикає 2/3 колонки від 40rem; поруч сторінка резервує outline 18–23rem (:1343–1347). За певних ширин viewport формально великий, а документ вузький. Це ризик стиснутих колонок, що потребує перевірки на реальній сторінці; доцільно прив'язати стек до доступної ширини документа.
5. **Зображення мають добру базу, але не повний набір станів.** Є `figure`, `alt`, пропорційний max-width (`LessonDocumentView.tsx:51–55,73–76`; `main.css:1360–1364`). Немає width/height чи UI невдалого завантаження. Розміри upload повертає (`domain/document/document.ts:127–131`), але image-секція їх не зберігає (:42–47). Резервування точних пропорцій — не «додати два CSS-рядки»: потрібне окреме рішення про дані. Не обрізати навчальні зображення через фіксований aspect-ratio/object-fit:cover.

ФАКТ: базовий reader уже має правильний напрям: React-екранування, семантичні p/h2/h3/списки/figure, responsive grid та нуль Tiptap-імпортів. Переписувати рендерер заради оформлення не потрібно.

#### 4. Що не чіпати / поза скоупом

- **Модель документа, санітизацію й серверні контракти.** `domain/document/document.ts:14–55` і конвертер — не дизайн-конфіг. Не додавати HTML, code-block, довільні embed чи довільну вкладеність заради toolbar. `tiptap-document.ts:80–107,110–123` відкидає невідомі вузли й бере перший paragraph listItem; перед розширенням WYSIWYG потрібний окремий round-trip доказ. Paste/nested-list/soft-break поведінку цей огляд не відтворював, отже не видає її за встановлену втрату даних.
- **Lazy-межу editor/reader.** Reader лишається чистим семантичним React (`LessonDocumentView.tsx:1–12`), Tiptap — в admin async-піддереві (`routes/admin.courses.$courseId_.lessons.$lessonId.tsx:5–12`). Спільна типографіка не означає імпорт редактора в reader.
- **Правила публікації, доступу й медіа.** Зберегти явні Save/Publish, optimistic-lock, draft/published, авторизований `/media/i/`, один player, транскрипт, прогрес і дискусію. Покращення повідомлень не є дозволом змінити ці механізми.
- **NorthWind shell, глобальну палітру, шрифти, dashboard-патерни.** Не переносити в білдер KPI-картки `StatTile`, графіки `TrendChart`, декор-glow чи таблиці лише тому, що вони є в kit. Inter/Space Grotesk і брендова палітра вже обрані репо; anti-slop не є підставою їх замінити. Наявні суперечності Tailwind/theme задокументовані, а не «виправлені» цим оглядом.
- **Gallery/portfolio/before-after, multi-video, здачу завдань, перекладацький UI, автозбереження та історію ревізій.** Це окремі продуктні механізми за `spec.md:105–136`; косметичний прохід їх не потребує. Вільне drag-полотно й редизайн усієї адмінки також не входять.

РІШЕННЯ (Codex, рекомендація 2026-10-13): наступна реалізація починається з QW1–QW3; перед розширенням масштабу — порівняння тих самих документів у editor і reader. Перевірка рекомендації: автор бачить поле й результат своєї дії, учень розрізняє пояснення та завдання; для цього не потрібна нова схема чи drag-рушій.

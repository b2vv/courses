# Спайк edge — що виміряно, а не передбачено

Одноразовий спайк перед редакцією 4 плану. Мета: перевірити найризикованіше рішення фази
там, де воно єдине може бути перевірене — у запущеному nginx. Робочий конфіг, що пройшов усі
перевірки, — [spike-edge.conf](spike-edge.conf).

| | |
|---|---|
| Дата | 2026-09-07 |
| Стенд | `nginxinc/nginx-unprivileged:1.30.4-alpine`, `--read-only`, `--tmpfs /tmp`, `--tmpfs /var/cache/nginx`, том із фікстурою на `/media:ro` |
| Апстрім | заглушка на Python із керуванням режимом (`allow` / `401` / `403` / `500` / затримка) і лічильником звернень |
| Причина | три раунди GATE 2 показали, що найважчі дефекти щоразу знаходив той, хто **запускав**, а не читав |

## 1. ВИПРАВЛЕНО 2026-09-07: перша знахідка була названа невірно

**Що я спершу записав:** «`proxy_cache_path` змінює поведінку старту — щойно він зʼявляється,
nginx створює всі temp-каталоги, і edge не стартує. Продакшн живий лише тому, що кеша немає.»

**Що виявилось при перезапуску спайку:** конфіг **без жодного кеша** падає так само:

```
[emerg] mkdir() "/var/cache/nginx/fastcgi_temp" failed (13: Permission denied)
```

**Справжня причина.** nginx створює ці каталоги на старті **незалежно** від кеша. Продакшн
стартує тому, що `infrastructure/nginx/nginx.conf` **рядки 8–12 уже перенаправляють усі пʼять
temp-шляхів у `/tmp`** — я їх не побачив, бо грепав конфіг лише на зони, формат логу й
локації. Підтверджено в живому контейнері: `/tmp/client_temp` і `/tmp/fastcgi_temp` існують і
належать `nginx`, а `/var/cache/nginx` порожній саме тому, що ним ніхто не користується.

**Наслідок для плану:** твердження «кеш завалив би деплой» — **неправда**. Додавання
`proxy_cache_path` нічого б не зламало. Зламався мій спайк-конфіг, бо в ньому бракувало
редиректів, які в продакшені вже є.

**Що з цього лишається корисним:** для будь-якого нового nginx-конфігу в цьому репо треба
переносити всі пʼять `*_temp_path` разом із рештою — інакше він не стартує під
`read_only` + tmpfs. Це справедливо, але це властивість **образу й монтувань**, а не кеша.

**Урок, який дорожчий за саму знахідку.** Це третій випадок у цій фазі, коли я з правильного
спостереження зробив хибний висновок про причину: спершу «`proxy_cache` без ключа» пояснив
властивістю образу, потім прочитав прогрітий кеш як «вікно витіснення» замість дірки, тепер
це. Запуск дає **факт**; причину все одно доводиться доводити окремо, і саме на цьому кроці я
тричі підставив те, що очікував побачити.

## 2. Префікс шляху працює як задумано

`/media/p/<playbackId>/hls/<videoId>/...` + `rewrite` + `root`:

| Перевірка | Результат |
|---|---|
| плейлист через префікс | **200** |
| сегмент через префікс | **200** |
| відносний URL усередині плейлиста (`v0/index.m3u8`) | лишається під префіксом — виконує вимогу ADR 005 «relative playlist URLs must retain credentials» |
| `Range: bytes=0-1023` | **206**, рівно 1024 байти |
| `/media/hls/…` без префікса | **403** |
| `/media/p/<id>/hls/../../source/<id>/original` | **403** |
| `%2e%2e`-обхід | **403** |
| кривий `playbackId` | **403**, без звернення до Go |
| кривий `videoId` | **403**, без звернення до Go |

**`{n}` у `rewrite` треба закавичити.** Без лапок nginx читає `{` і `}` як межі блоку:
`directive "rewrite" is not terminated by ";"`. У `map` лапки вже стоять, у `rewrite` я їх
спершу забув — конфіг не піднявся.

## 3. Кеш: вмикається, ізолює, і секрету в ньому немає

| Перевірка | Результат |
|---|---|
| три однакові запити при апстрімі з `Cache-Control: no-store` | **1** звернення до апстріму — `proxy_ignore_headers` працює |
| ключ — `playback\|video`, не файл | один `authorize` покриває **всі** файли відео |
| `P1`, `P2`, `P1` | два звернення: другий `P1` узято з кеша, `P2` — окремий запис |
| вміст файла кеша (`strings … \| grep ^KEY:`) | `KEY: <playbackId>\|<videoId>` — **сесійного токена немає** |

Остання строка закриває конституційну знахідку рецензента: у редакції 3 ключем була сесійна
кука, і сирий токен лягав у файл відкритим текстом. Префікс шляху усуває це **конструкцією**,
а не помʼякшенням.

**Побічно виміряне вікно витіснення.** Закешоване «так» пережило зміну відповіді апстріму —
рівно `proxy_cache_valid`. Це і є число з A32, і воно спостережуване.

## 4. Нормалізація відмов і відділення інфраструктури

| Апстрім | Клієнт | Навіщо |
|---|---|---|
| `204` | **200** | дозвіл |
| `403` | **403** | відмова |
| **`401`** | **403** | `Handler.Authenticate` віддає 401; без нормалізації анонім діставав би 401, а не-власник 403 — це розрізнення, яке **A7 забороняє** |
| `500` | **503** | інфраструктура, ретраїбельно |
| апстрім недоступний | **503** | те саме |
| кривий id | **403** | гард, Go не турбують |

**`error_page` із 503 у списку — самопосилання.** `error_page 500 502 503 504 = @unavailable`
разом із `@unavailable { return 503; }` замикається сам на себе. У списку лишаються
`500 502 504`.

## 5. Навантаження: таймаути редакції 3 давали 2% хибних відмов

| Конфігурація | 400 запитів, 20 паралельно, холодні ключі |
|---|---|
| `connect 1s` / `read 2s` (редакція 3) | **392 × 200, 8 × 403** — 2% глядачів дістали термінальну відмову при живому апстрімі |
| `connect 2s` / `read 5s` + відділений 503 | **400 × 200** |

Отже твердження редакції 3 «падіння Go коротше за 30 с невидиме» було неправдою для
холодного ключа, і причина — не архітектура, а занижені таймаути.

## 6. Дві методичні помилки спайку, названі вголос

- **Хибна знахідка через власні тестові дані.** Ідентифікатори виду `g…`, `h…`, `i…` не є
  шістнадцятковими, тож `map` не збігався і 403 приходив від мого гарда, а не від
  `error_page`. Це дало хибний висновок «апстрім 500 → 403», який тримався три прогони.
  Виправлено переходом на `printf '%032x'`. Побічна користь: підтвердилось, що гард
  відсікає кривий id **до** звернення в Go.
- **Застарілий IP апстріму.** Після `docker stop`/`start` nginx далі бив у старий IP, бо
  резолвить імʼя один раз на старті. Це рівно причина, чому продакшн-конфіг усюди
  використовує `set $var` разом із `resolver 127.0.0.11 valid=5s` — конвенцію треба зберегти
  і для `/_media_auth`.

## 7. Що з цього йде в редакцію 4

1. Усі пʼять temp-шляхів у `/tmp` — інакше edge не стартує. **Але це не наслідок кеша**:
   у продакшн-конфізі вони вже є (рядки 8–12), тож для §3 нічого додавати не треба.
2. Ідентифікатор відтворення в префіксі шляху: закриває дві вкладки, відсутність
   `user_sessions.id` і секрет у ключі кеша — **три blocking одним рішенням**.
3. `error_page 401 403 = @denied` (403) і `error_page 500 502 504 = @unavailable` (503).
4. Таймаути `connect 2s` / `read 5s`.
5. `set $api …` + `resolver` для `/_media_auth`.
6. Лапки навколо `{n}` у `rewrite`.
7. Приймальні рядки, які тепер мають виміряні очікування, а не припущені.

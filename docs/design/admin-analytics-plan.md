## 0. Чому «даних нема» (корінь)

Звірено з кодом (admin-surface, 2026-10-10): **жодного stats / aggregate / summary / time-series ендпоінта.** Повний admin-API: `courses` (offset-пагінація → є `pagination.total`), `users` (те саме), `instructors`, `learners` (**cursor, без total**), `participant-reports` (**cursor, без total**), `lessons/videos` (поштучно). Orders — лише `/learn/orders/{id}` поштучно, **admin-агрегату замовлень/доходу нема**.

Наслідок: «реально зараз без беку» = лише `pagination.total` там, де offset-пагінація: **users за статусом (3)** і **courses за статусом (3)** + два total-и. Усе інше — роль, enrollments, orders/дохід, залученість, навантаження модерації, будь-що **в часі** — недосяжне без нового беку. Кільце на один status-count — косметика, не аналітика. **Справжня аналітика = спроєктувати backend stats-шар.**

## 1. Призначення — які питання адмін платформи курсів реально ставить

- **Люди:** скільки акаунтів; активні/заблоковані/видалені; за роллю (student/instructor/admin); нові за період; верифіковані; з 2FA.
- **Контент:** скільки курсів; чернетки/опубліковані/архів; по інструкторах; нові/оновлені.
- **Доступ і продажі:** членства (grants) за станом active/blocked/revoked; замовлення approved/declined/pending; дохід; конверсія перегляд→купівля.
- **Залученість:** активні учні за період; середній прогрес; завершення курсів.
- **Модерація:** відкриті скарги; навантаження черги; заблоковані автори; скарги на людей vs на контент.
- **Операції:** відео в обробці/ready/failed; ASR-чернетки; черга транскодування.

## 2. Каталог метрик (домен → метрика → джерело → вартість)

🟢 є зараз (count-запит `limit=1`, беремо `pagination.total`) · 🟡 частково/дорого · 🔴 треба бек.

**Люди**
- Акаунтів за статусом (active/blocked/deleted) — 🟢 3× `users.list({status})`.
- Усього акаунтів (active+blocked; deleted дефолт виключає) — 🟢.
- За роллю (student/instructor/admin) — 🔴 (нема фільтра за роллю в `AdminUserQuery`).
- Нові акаунти за період — 🔴 (нема часу/created_at у вибірці).
- Верифіковані / з 2FA — 🔴 (нема полів у моделі `AdminUser`).

**Контент**
- Курсів за статусом (draft/published/archived) — 🟢 3× `courses.list({status})`.
- По інструкторах — 🟡 (є `instructors`; розподіл = N запитів або бек).
- Нові/оновлені за період — 🔴 (нема часових бакетів).

**Доступ і продажі**
- Grants за станом (active/blocked/revoked) — 🔴 (нема admin-агрегату grants).
- Замовлення за статусом / дохід — 🔴 (**нема admin-orders-ендпоінта взагалі**).
- Конверсія — 🔴.

**Залученість**
- Активні учні / середній прогрес / завершення — 🔴 (`learners` cursor без total; прогрес поштучно).

**Модерація**
- Відкриті vs закриті скарги — 🔴 (`participant-reports` cursor без total).

**Операції (медіа/ASR)**
- Відео за станом — 🟡 (список відео повний per-course → рахується клієнтом у межах курсу; глобально 🔴).

**Висновок:** без беку чесно показуються ~6 чисел (users×3, courses×3). Усе цінне (роль, продажі, залученість, тренди) — 🔴.

## 3. Бекенд stats-шар (ключовий анлок)

Один новий ендпоінт замість N крихких count-запитів, і він відмикає все 🔴:

- **`GET /api/v1/admin/stats`** → знімок (один SQL-прохід `COUNT(*) … GROUP BY` на індексованих колонках, дешево):
  ```
  {
    users:   { active, blocked, deleted, byRole: {student,instructor,admin}, verified, twoFactor },
    courses: { draft, published, archived },
    grants:  { active, blocked, revoked },
    orders:  { approved, declined, pending, refunded, revenueMinorUAH },
    reports: { open, resolved },
    media:   { processing, ready, failed }
  }
  ```
- **`GET /api/v1/admin/stats/timeseries?metric=&bucket=day|week&from=&to=`** (етап C) → `[{ bucketStart, value }]` для signups / enrollments / orders / revenue. Рахується з `created_at`-бакетів (`date_trunc`). Потребує, щоб у таблиць був надійний `created_at` (у більшості є).

Чому так, а не N фронт-count-ів: (1) одне джерело правди, (2) роль/grants/orders/reports недосяжні count-запитами взагалі, (3) один раунд-тріп замість десятка, (4) можна кешувати. Ризик: тримати знімок актуальним (без матеріалізації — просто COUNT при запиті; для платформи такого розміру дешево).

## 4. Структура сторінки (NorthWind, §4.7/§5)

Окрема `/admin/analytics` (або розширений `/admin` Overview — див. §6). Hero-банд (ui-stat × 3–4): усього акаунтів · усього курсів · дохід (після stats) · відкриті скарги. Нижче — картки-секції:
- **Люди:** кільце статусів + розподіл за роллю + sparkline нових (після timeseries).
- **Контент:** курси за статусом + останні оновлені.
- **Доступ і продажі:** grants за станом + замовлення + тренд доходу.
- **Залученість:** активні учні · середній прогрес · завершення.
- **Модерація:** відкриті vs закриті · навантаження черги.
- **Операції:** медіа/ASR стани.

Правило: картка без даних **деградує чесно** (плейсхолдер «потребує stats-ендпоінта»), а не показує вигадане число (дисципліна плану §0, R1).

## 5. Що показує кільце (якщо все-таки робимо тонку версію зараз)

Розподіл акаунтів за статусом, 3 реальні count-и: Активні (`--color-success`), Заблоковані (`--color-danger`), Видалені (`--color-muted`). Центр = сума трьох = «усього акаунтів» (НЕ «Усі», бо фільтр-«Усі» = active+blocked, дефолт виключає deleted — інакше два різні числа на екрані). Без ролі (🔴), без тренду (🔴).

## 6. Зв'язок із reconstruction S1 Overview

Плановий S1 `/admin` Overview — це тонка версія цього. Варіанти: (а) `/admin` Overview = hero-банд + топ-картки, а `/admin/analytics` — повна аналітика; (б) один екран. **Рішення власника потрібне.**

## 7. Фазування (чесно)

- **A0 (зараз, 🟢, без беку):** лише 6 реальних count-ів (users×3 + courses×3 + totals). Це чесний мінімум-блок на Overview, **не** окрема «Аналітика».
- **B (окремий бек-етап):** `GET /admin/stats` (SQL GROUP BY) → справжня аналітика-знімок (роль, grants, orders/дохід, reports, media).
- **C (пізніше):** `timeseries` → тренди/дельти (потребує created_at-бакетів; «нові за тиждень», «дохід за місяць»).

## 8. Рішення, яких бракує (для власника)

1. Окрема `/admin/analytics` vs розширений `/admin` Overview (§6)?
2. Revenue/orders-аналітика потрібна зараз? (прод у sandbox — дохід поки 1-UAH тести; можливо, відкласти до реальних платежів).
3. Тренди в часі (етап C) треба, чи знімка (B) досить? Тренди = помітно більше беку.
4. Пріоритет: аналітика (B) vs решта reconstruction (S3/S4/S5) vs функціональні прогалини (confirm-delete, 2FA-reset-у-UI, зміна ролі)?

**Рекомендація:** це фактично нова міні-фаза «admin stats», не слайс reconstruction. Спроєктувати детально (spec-flow: spec→gate→plan) свіжою сесією; зараз — зафіксувати цю чернетку й вибір власника по §8. Для reconstruction S1 Overview поки показати лише A0 (6 чесних count-ів) або відкласти Overview до етапу B.

### 8.1. Рішення власника (2026-10-10, прямо в сесії)

Автор рішення: власник репо (strelchenko.dev), зафіксовано Courses під час сесії
`feat/admin-reconstruction`. Кожне закриває альтернативу.

1. **Пріоритет (§8.4):** брати в роботу **аналітику-мінфазу (етап B) через spec-flow** —
   нова міні-фаза «admin stats», а не слайс reconstruction і не функціональні прогалини.
   *Перевірка:* наступний durable-артефакт — `docs/<admin-stats>/spec.md` за spec-flow, не
   черговий S3/S4 коміт у reconstruction.
2. **Revenue (§8.2):** **включити orders/дохід у stats-шар одразу.** Потребує нового
   admin-orders-агрегату (зараз немає взагалі, §2 «Доступ і продажі» 🔴).
   *Перевірка:* `GET /admin/stats` повертає `orders{approved,declined,pending,refunded,
   revenueMinorUAH}` з реального SQL-проходу по orders, не заглушку.
3. **Глибина (§8.3):** **знімок + тренди (B+C) разом.** Крім `GET /admin/stats` будувати
   `GET /admin/stats/timeseries` одразу. Передумова — надійний `created_at` у задіяних
   таблицях (перевірити при специфікації; §7 C).
   *Перевірка:* обидва ендпоінти в spec; timeseries дає `[{bucketStart,value}]` з
   `date_trunc`-бакетів для signups / enrollments / orders / revenue.
4. **§8.1 напрямок (був §9.1):** повний `/admin/analytics` спершу, дашборд/Overview —
   курована підмножина пізніше. Single-instructor (§9.2) — конфіг-прапорець над тими самими
   віджетами, не окрема гілка коду.

Відкрите (не блокує старт spec): точний перелік таблиць без `created_at` (вирішиться на
spec-етапі звіркою зі схемою).

## 9. Інтернет-ресерч зрілих платформ (2026-10-10)

Повний каталог аналітики 12+ платформ (Teachable/Thinkific/Kajabi/Udemy/Skillshare/LearnWorlds/Podia/Moodle/Canvas/TalentLMS/Circle/Gumroad/MasterStudy) з джерелами — `docs/design/admin-analytics-research.md`. Ключове звідти:

**ТОП-5 віджетів** (покривають усі 4 запити власника, є у 4+ платформах): (1) дохід за період, (2) топ-курси за enrollments/доходом, (3) enrollments за період, (4) watch time по курсах, (5) retention/drop-off по відео + топ/анти-топ лекцій. Далі: completion rate, per-instructor панель, нові реєстрації, conversion visit→buyer. Churn/MRR/cohort — свідомо НЕ в топі (ми не підписка).

**Підтверджено:** жоден із ТОП-12 не реалізується без нового stats-шару (§3). 🟢 зараз лише users×3 + courses×3. Найдорожчі — retention/drop-off (потребує подієвого збору позицій відтворення) і conversion (нема обліку переглядів sales-page узагалі).

### 9.1. Дашборд = курована підмножина повного розділу (рішення власника напрямку)
Власник (2026-10-10): «коли буде повноцінний розділ аналітики, тоді можна виносити щось у дашборд». Тобто два рівні: спершу **повний `/admin/analytics`** (усі секції §4), потім **дашборд/Overview** = курований shortlist ТОП-віджетів із нього. Не будувати дашборд першим — він похідний.

### 9.2. Налаштування single-instructor (вимога власника)
Прапорець порталу `platform.singleInstructor`. Для solo-платформ (Teachable/Thinkific/Kajabi/Podia/Gumroad) виміру «інструктор» нема взагалі. Коли прапорець `true`:
1. Ховати секцію/картку «Інструктори» (віджет #7) повністю.
2. Прибирати колонку й фільтр «інструктор» у таблицях курсів і розбивках доходу/enrollments/watch.
3. Не показувати per-instructor порівняння/leaderboard.
4. Overview курсо-центричний: «дохід по курсах» / «топ-курси», не «по авторах».
5. Трактувати автора як сам портал (без split platform↔instructor).

**Принцип:** віджети проєктувати З виміром «інструктор» одразу, а прапорцем лише ПРИХОВУВАТИ — поява 2-го лектора не вимагає переробки. Це додає до §8 рішення: single-instructor — не окрема гілка коду, а конфіг-прапорець над тими самими віджетами.

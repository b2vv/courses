## 2. Бриф (design-pass §2)

- Тип артефакту: `system` (≈25 поверхонь трьох поверхонь-щільностей: storefront/client, learn, admin/teach).
- Мета: кожен екран має зрозумілу ієрархію й основну дію, повний основний сценарій і **докази** на 4 viewport + 200% тексту; blocker/major виправлено й перевірено повторно.
- **Non-goals:** редизайн або новий стиль; нові фічі/стани, яких немає; зміна бізнес-поведінки, API, бекенду; перемикач теми; production-деплой.
- Acceptance-база: чинні acceptance фаз, які володіють екранами (catalog, accounts, playback/learning, admin, teach-editor, multi-audio…). Design-pass їх **не змінює**; UI-перевірки нижче — запропоновані доповнення, не прийняті до погодження.

## 10. Зріз AUTH — A1/A2/A4/A5 (власник 2026-11-16: «Спершу auth-зріз»)

**Scope / acceptance.** Закрити S0 A1-1 (blocker), A2-1, A5-1 і тупик A4 (сторінка «Забули пароль» без шляху назад; той самий сценарій відновлення). Спостережувана поведінка:
- **AUTH-1.** На `/login` (крок пароля) є посилання «Забули пароль?» → `/password/forgot` і «Зареєструватися» → `/register`. На кроці 2FA й у стані «вже увійшли» їх немає.
- **AUTH-2.** На `/register` завжди є «Вже маєте обліковий запис? Увійти» → `/login`. За `email_taken` до помилки додається «Скинути пароль» → `/password/forgot`.
- **AUTH-3.** На `/password/forgot` є «Згадали пароль? Увійти», а в стані «лист надіслано» — «Повернутися до входу».
- **AUTH-4.** На `/password/reset` без токена, а також після відповіді `invalid_account_token` / `token_used`, форми немає. Замість неї — заголовок стану, пояснення й основна дія «Запросити нове посилання» → `/password/forgot`. З валідним токеном усе як було; `weak_password` і помилки мережі лишають форму.

**Правило `401` (одне для членства, авторства, «Записатися» й «Купити курс»).** Будь-яка відповідь `401` → одне перечитування сесії (`/me`): аноним → рядок гостя (A6/A7) цієї ж сторінки; перечитування не вдалося → A2; сесія є → **один** автоматичний повтор запиту читання (членство/авторство). Другий `401` при підтвердженій сесії в тому самому циклі (той самий користувач і курс) → A2 з ручним «Спробувати ще раз», без нових автоматичних запитів. Запис і купівля ніколи не повторюються автоматично: після перечитування користувач натискає сам.

Автор-викладач, що не автор цього курсу (`403 course_forbidden`), іде рядками A5–A9 як будь-який користувач. Для сесії без ролі `instructor` запит авторства не робиться (`owner` = ні одразу).

### Факти (звірено з кодом на `cbad6649`)

### Рішення

**R1. Один `RouterProvider` для всього застосунку.** Ставиться в `__root.tsx` (`Document`, усередині TanStack-роутера, над обома оболонками):
- `navigate = (href, options) => router.navigate({ href, ...options })`;
- `useHref` не передається: типове значення провайдера — тотожність (`openLink.mjs:33`). Без `basepath` SSR і клієнт рендерять той самий `href`, тож розбіжності гідратації немає.

Тип `routerOptions` реєструється через `declare module 'react-aria-components' { interface RouterConfig { routerOptions: { reloadDocument?: boolean; replace?: boolean } } }`. Модуль, де `RouterConfig` фактично оголошено (`@react-types/shared/src/dom.d.ts:231`, реекспорт через `react-aria-components`), звіряється під час typecheck. Тип `href` лишається `string`: посилання каталогу будують рядок разом із пошуком.

**R2. Перехід між поверхнями — повне завантаження, як зараз.** Поверхня визначається за шляхом: `workspace` = `/admin`, `/admin/*`, `/teach`, `/teach/*`; решта — `client`. Якщо поверхня поточного й цільового шляху різна, `navigate` додає `reloadDocument: true`. Те саме ставиться на TanStack `Link` у `AdminShell.tsx:93` (`to="/"`), єдиний наявний перехід між поверхнями без перезавантаження.

- *Механізм:* записи адмінки й викладача не інвалідують публічних ключів (`admin-queries.ts:51-61`), а публічні дані живуть у кеші 60 с. Переглянутий в адмінці курс після правки показав би стару сторінку. Повне завантаження скидає кеш, тому поведінка лишається такою ж, як до зрізу.
- *Відкинута альтернатива:* інвентар усіх записів адмінки, викладача, відео й документів з інвалідацією публічних ключів. Її ціна — кожен запис у кількох модулях і нова точка забуття.

**R3. Повтор після помилки — повне завантаження.** `ErrorState` з `retryHref` передає `routerOptions={{ reloadDocument: true }}`. Семантика G0 #6 «повтор перезавантажує ту саму адресу» зберігається: свіжий SSR і новий кеш, без залежності від того, чи перезапустить роутер завантажувач для тієї самої адреси.

**R4. Фокус після навігації.** Перевірка робиться один раз на кожну завершену навігацію без перезавантаження. Вона виконується в `useEffect` на зміну `resolvedLocation` (`useRouterState`), тобто після коміту нової сторінки, коли зниклі елементи вже прибрано з DOM. Фокус переходить на `#main` (`focus({ preventScroll: true })`; прокрутку веде `scrollRestoration`), якщо виконано одну з умов:
- (а) змінився `pathname`, тоді фокус переходить завжди;
- (б) `pathname` той самий, а фокусу немає ніде: `document.activeElement` — це `body` або `null`.

У решті випадків фокус лишається, де є. Сюди входять зміна лише пошуку чи хешу, коли сфокусований елемент пережив навігацію (сортування, «Наступна» не на останній сторінці), і випадок, коли користувач під час повільної навігації сам перевів фокус на контрол поза рамкою очікування маршруту: хедер, меню, футер, перемикач мови. Ці контроли переживають відповідь. Перше завантаження (`resolvedLocation` без попередника) фокус не рухає. Back/Forward поводиться так само, як клік.

Випадок (б) покриває межі пагінації: на першій сторінці зникає «Попередня», на останній — «Наступна». Покриває він і повільну пагінацію, коли `CatalogListLoading` замінює список і навігацію, а фокус падає на `body`.

**R4a. Контроли рамки очікування каталогу неінтерактивні.** `CatalogFrame` (`CatalogView.tsx:26`) отримує проп `controlsInert`, який ставить `inert` лише на `<form className="catalog-search">`. `CatalogListLoading` (`CatalogStates.tsx:22-29`) передає його. Поля пошуку й сортування видно, але сфокусувати їх, клікнути чи щось набрати неможливо.

Заголовок `h1` і скелетон (`children` рамки) — сусіди форми, а не її нащадки, тож лишаються в дереві доступності. Скелетон зі своїм `role="status"` («Завантажуємо курси») і далі оголошується. `inert` на всій рамці сховав би й статус (HTML Standard, «inert subtrees»).

- *Механізм проблеми:* `pendingComponent` (`courses.index.tsx:28,41-43`) і `CatalogRoute` — різні дерева. Поле, сфокусоване або заповнене в рамці очікування, після відповіді розмонтовується разом із текстом.
- *Що це дає:* фокус не потрапляє в рамку, яка зникне, тож випадок (б) R4 не спрацьовує посеред набору, і текст не губиться.
- *Відкинуто:* (1) рамка поза піддеревом очікування з `keepPreviousData` замість `pendingComponent` — переписує завантаження каталогу з C2, а зникнення посилань пагінації після приходу даних однаково потребувало б окремого правила фокусу; (2) відновлення фокусу за `name` нового контролу — набраний текст однаково губиться.

Рамка помилки (`CatalogListFailure`) — кінцевий стан, лишається інтерактивною.

**Гонки.** Нова навігація під час попередньої скасовує її завантажувач (`abortController` маршруту). Ефект прив'язаний до `resolvedLocation` останньої завершеної навігації, тож проміжна скасована навігація його не запускає. Підписок немає, отже немає й відписки.

Одне «в процесі» на всі кнопки: хук використовує спільний `mutationKey` і `useIsMutating`; поки йде будь-який запит повторного надсилання, натискання будь-якої з кнопок ігнорується, кнопки мають `isPending` (не `isDisabled` на сфокусованій кнопці — пастка `isdisabled-on-focused-button-drops-focus`). Результат показує лише та поверхня, з якої натиснули (власний стан мутації кожного екземпляра хука), тож його оголошують один раз. Кілька вкладок — поза межами: кожен запит інвалідує попередні посилання, і текст 204 це прямо каже.

**V2 — стани `/verify-email` (#3, #5; разом з V1).** Стан маршруту рахується від поточного токена (V4a) і сесії; перший рядок, що підходить, виграє:

| # | Умова | Заголовок | Текст | Дія |
|---|---|---|---|---|
| S1 | запит перевірки ще йде | «Підтверджуємо пошту» | «Перевіряємо посилання…» | — |
| S2 | 204 | «Пошту підтверджено» | як зараз | увійшов → «До навчання» (`/learn`); гість або сесію не прочитано → «Увійти» (`/login`; для того, хто вже увійшов, `/login` має свій стан «Продовжити») |
| S3 | збій посилання або невизначений збій, і після свіжого читання сесії пошта підтверджена | «Пошту вже підтверджено» | «Можна продовжувати навчання.» | «До навчання» |
| S4 | збій посилання (`invalid_account_token`, `token_used`, `invalid_request`, відсутній токен) | «Посилання не працює» | «Посилання недійсне або вже використане.» | V1: гість (або сесію не прочитано) — поле пошти + «Надіслати лист знову»; увійшов і не підтвердив — лише кнопка |
| S5 | невизначений збій (мережа, тайм-аут, 5xx, невалідна відповідь, 429) | «Не вдалося перевірити посилання» | «Можливо, пошту вже підтверджено. Перевірте ще раз.» | «Перевірити ще раз» |

S3 потребує свіжого `current()`: після S4/S5 для того, хто увійшов, маршрут перечитує сесію (`fetchQuery` зі `staleTime: 0`) і лише тоді вибирає між S3 і S4/S5. «Перевірити ще раз» (S5): той, хто увійшов, — перечитує сесію (підтверджено → S3) і, якщо ні, повторює запит тим самим токеном; гість — повторює запит. Повтор, що отримав `token_used`, веде в S4: там є шлях до нового листа (для гостя — поле пошти), тож відновлення не залежить від того, чи перший запис відбувся. Повторне натискання під час запиту ігнорується.

**V4 — спільне для A3 і A6.**
- **V4a. Стан належить токену.** Тіло маршруту монтується з `key` = токен (або «немає»): новий токен через зміну пошуку — новий стан і нова автоматична відправка; відповідь для попереднього токена не показується, бо її екземпляр розмонтовано.
- `aria-busy` на секції під час запиту.
- Мітка над заголовком в A6 — «Підтвердження пошти», як в A3 (taste).

**V5 — фокус у картці 2FA (#6).** Коли вміст картки замінюється дією користувача, фокус переходить на перший текст нового вмісту (елемент із `tabIndex={-1}`), щойно той відрендерився (ефект на зміну фази картки):
- «Увімкнути 2FA» → текст налаштування («Відскануйте цей QR-код…»);
- «Підтвердити 2FA» з успіхом → рядок «2FA увімкнено.» над кодами (V14);
- «Готово» (V14) → рядок «2FA увімкнено.»;
- «Скасувати» (V8) → кнопка «Увімкнути 2FA»;
- «Вимкнути 2FA» з успіхом → рядок «Захист 2FA ще не ввімкнено.»;
- «Отримати нові резервні коди» з успіхом → рядок над новими кодами.
Перше відображення сторінки фокус не рухає. Помилка не змінює вміст і не рухає фокус (alert читається сам).

**V5a — стан картки задає успіх мутації.** Успіх «Підтвердити 2FA» одразу записує `twoFactorEnabled: true` у кеш `current()` (`setQueryData`; на сторінці є спостерігач `useQuery`, тож запис не зникне), а повторне читання йде у фоні; успіх «Вимкнути 2FA» — `false`. Тож «Готово» і фокус не залежать від того, чи встигло читання `/me`. Будь-яка помилка «Підтвердити 2FA», крім `invalid_totp`, перечитує `current()`; якщо 2FA уже ввімкнена (сервер вмикає до створення кодів) — картка показує стан «увімкнено» з повідомленням «2FA увімкнено, але резервні коди не отримано. Отримайте нові коди нижче.», фокус на ньому. Так само невизначена помилка «Вимкнути 2FA» перечитує стан.

**V6 — повідомлення полів мовою сторінки (#7; клас: усі `TextField`/`TextArea`).** `TextField` і `TextArea` передають у `Aria.FieldError` типовий текст, коли поле не має `errorMessage`: функція від `validationDetails` — `valueMissing` → «Заповніть це поле.», `typeMismatch` для `type="email"` → «Введіть адресу електронної пошти.», `tooLong`/`tooShort` → «Перевірте довжину значення.», будь-що інше → «Перевірте значення.». Явний `errorMessage` має перевагу. `Select`/`ComboBox` не змінюються. Тексти — нові ключі `form.*` у uk/en. Зачіпає всі форми з `isRequired` (перелік у «Фактах») → повний e2e.

**V7 — 2FA увімкнено: дві окремі групи (#8).** Картка = рядок стану + дві групи, кожна — `role="group"` з `aria-labelledby` на свій `h3` і власною помилкою під своєю кнопкою (джерело помилки — мутація цієї групи):
1. «Резервні коди» — «Нові коди замінять попередні.», поле «Код автентифікатора або резервний код», кнопка «Отримати нові резервні коди» (secondary);
2. «Вимкнути 2FA» — «Поточний пароль», «Код автентифікатора або резервний код», кнопка «Вимкнути 2FA» (danger) — останньою.
Мітки полів однакові, бо обидві дії приймають і TOTP, і резервний код; поля розрізняє ім'я групи.

**V8 — «Скасувати» в налаштуванні 2FA (#9).** Secondary-кнопка поруч із «Підтвердити 2FA»: прибирає налаштування на клієнті без запиту (див. «Факти»), очищає поле коду, повертає «Захист 2FA ще не ввімкнено.» + «Увімкнути 2FA», фокус — V5. Під час запиту підтвердження натискання «Скасувати» ігнорується.

**V9 — поточна пошта (#10).** Над полем картки пошти: «Поточна пошта: {email}» з `current()`. Поки сесія читається або не прочиталась — рядка немає (сторінка захищена `requireIdentity`).

**V10 — після збереження форма порожня й успіх помітний (#11).** Після 204 зміни пароля обидва поля очищаються; після 204 зміни пошти — поле. Повідомлення успіху (`<output>`) отримує клас `.form-success` (колір `--color-success`); контраст — axe у світлій і темній темі. Нова відправка прибирає попередній успіх.

**V11 — кнопки власної ширини (#12).** У картках налаштувань кожна дія, що не є полем, — власної ширини на початку рядка: діти форм (`.account-settings-card form > :not(.ui-field)`) і прямі діти картки (`.account-settings-card > .ui-button`, ряд дій кодів), те саме правило, що `.notice form` (AUTH). Дії кодів — в один ряд із переносом (`.cluster`). Кожну з трьох кнопок аудиту #12 міряють окремо.

**V12 — 200% без розриву слова (#13).** `.notice` отримує те саме, що `.status-page` у C3b: `container-type: inline-size` і `@container (max-width: 14em)` з `overflow-wrap: normal; hyphens: auto` для `h1, p, .ui-button`. Ризик: `inline-size`-контейнер не бере ширину від вмісту — на 6 в'юпортах міряють, що `.notice` не стискається.

**V13 — відступ дії від тексту (#14).** Пряма дія в `.notice` (кнопка, посилання-кнопка, форма повторного надсилання) — `margin-block-start: var(--space-4)`, як у A5.

**V14 — коди: «Готово», стан і копіювання (#15).** Над кодами — рядок «2FA увімкнено.» (або «Нові резервні коди» після регенерації); під ними — «Скопіювати коди» (secondary) і «Готово» (primary), що ховає коди на клієнті (вони й зараз не показуються після перезавантаження). Повідомлення «скопійовано» належить поточному набору кодів (блок кодів має `key` = набір; новий набір — новий стан); збій `clipboard.writeText` або відсутній буфер → `role=alert` «Не вдалося скопіювати. Виділіть коди й скопіюйте вручну.»; запізніле завершення копіювання для попереднього набору не показується.

**V15 — секрет читається повністю (#16).** Поле «Секрет для ручного налаштування» стає `TextArea` лише для читання (2 рядки, моноширинний шрифт, перенос будь-де); значення без пробілів не змінюється (e2e і застосунки читають його як є).

**Лист і посилання (`accounts.spec.ts`, наявний зареєстрований обліковий запис, без нового входу).**
1. Після реєстрації (увійшов, не підтверджено) запам'ятати ідентифікатор першого листа й посилання з нього (`readMailLink` отримує параметр «не цей ідентифікатор» / повертає ідентифікатор).
2. Окремий контекст без cookie: `/verify-email` → S4, поле пошти, відправка → текст 204; дочекатися листа з **іншим** ідентифікатором, узяти нове посилання.
3. У тому самому гостьовому контексті відкрити перше посилання → S4 «Посилання не працює» (сервер інвалідував його).
4. На сторінці того, хто увійшов, відкрити нове посилання → S2 + «До навчання».
5. Там само відкрити перше посилання ще раз → S3 «Пошту вже підтверджено».
